# From a release to an installed cask

Living document. It describes the workflows and the scripts that are in the
tree, and a change to either updates it.

Contracts: [`Casks/`](../../Casks/) and
[`.github/scripts/bump_casks.py`](../../.github/scripts/bump_casks.py).

## Overview

A cask installs a binary release of 1 application. The application's own
repository publishes that release, and the cask names its version, its
download URL and its sha256. Nothing in this repository builds an
application; the tap carries the release facts forward to a user's machine.

```
nsl release ──► GoReleaser (in frostyard/nsl) ──► bump/nsl-<version> PR
other release ──► bump.yml (bump_casks.py) ──► bump/<item>-<version> PR
  ──► brew test-bot (tests.yml) ──► merge, or brew pr-pull with the label pr-pull (publish.yml) ──► main
main ──► brew install --cask <item>
```

## 1. A release reaches the tap

There are 2 routes, and a file takes 1 of them.

**GoReleaser writes the cask.** On each stable release, `frostyard/nsl`'s
release configuration commits `Casks/nsl.rb` to a `bump/nsl-<version>` branch
of the tap and opens 1 pull request into `main`, titled
`fix(cask): bump nsl to v<version>`, with the `HOMEBREW_TAP_TOKEN` of the
machine account
([nsl ADR-0020](https://github.com/frostyard/nsl/blob/main/docs/adr/0020-homebrew-tap-publication.md)).
The release does not change `main`: a person reviews and merges that pull
request like a `bump.yml` pull request. A rerun for the same tag updates the
same branch. GoReleaser logs a refused pull request (HTTP 422) only as a
warning, so a green release job does not prove that the pull request exists:
after each `nsl` release, check the tap for it. The first line of the file
says `This file was generated by GoReleaser. DO NOT EDIT.` and its `livecheck`
stanza is skipped. A hand edit is lost on the next release, so a change to
that cask is a change to `nsl`'s release configuration.

**The bump workflow updates every other cask.** The schedule
(`0 3 * * *`, daily at 03:00 UTC) and `workflow_dispatch` (with the `dry_run`
and `base_ref` inputs) start
[`bump.yml`](../../.github/workflows/bump.yml). It sets up Homebrew, checks out
the workflow and a second checkout of the tap at `tap` (`fetch-depth: 0`, no
persisted credentials), configures git with `gh auth setup-git` and the
`github-actions[bot]` identity, and runs

```sh
python3 .github/scripts/bump_casks.py --tap-dir tap --base-ref "$BASE_REF"
```

with `GH_TOKEN` in the environment, plus `--dry-run` when the input asks for
it. The job grants `contents: write` and `pull-requests: write`, and the 2
checkouts keep no credentials, so the push and the API call use `GH_TOKEN`.

## 2. The bump script verifies before it writes

[`bump_casks.py`](../../.github/scripts/bump_casks.py) reads `Casks/*.rb` and
`Formula/*.rb`. For each file it fails closed, so a problem in 1 item is a
row with status `error` and the run exits 1:

1. A first line with the GoReleaser marker is skipped, with status
   `release-hook`.
2. It reads the version from the `version` line, or from the tag in the
   `url`.
3. It resolves the `owner/repo` of the
   `https://github.com/<owner>/<repo>/releases/download/` URL. More than 1
   repository in the file is an error.
4. It reads the latest release with `gh api repos/<slug>/releases/latest`. A
   version that is not older is `current`.
5. It maps every sha256 of the file to an asset of the release of the current
   version, by the asset's `digest`. A sha256 that maps to no asset is an
   error.
6. It downloads each new asset with `gh release download` and checks, in this
   order: the sha256 it computes equals the release digest; when the release
   has a `checksums.txt`, it lists the same value for the asset; `gh attestation verify
   --source-ref refs/tags/<tag>` accepts the artifact's build provenance. Any
   failure is an error.
7. For a cask tarball (`.tar.gz`, `.tgz`) it opens the archive and requires
   every literal `binary` and `artifact` path of the file to be a member.
8. It rewrites the version and the sha256 values, then runs `brew style` on
   the file. A style failure restores the file.
9. Unless `--dry-run` is set, it pushes `bump/<item>-<version>` and opens 1
   pull request into the base ref. A dry run prints the diff and restores the
   tap.

A bump branch always starts at the tap's ref at the start of the run, never at
another item's branch, and the tap is restored to that ref after each item. An
existing remote branch or an open pull request with the same head is
`pr-exists`. The script never pushes to the base ref; a person merges the pull
request. The step summary gets a Markdown table with 1 row per item. The pull
request body names the old and the new sha256 of each asset and the 3 checks
above.

## 3. A pull request is tested, then published

[`tests.yml`](../../.github/workflows/tests.yml) runs `brew test-bot` on a push
to `main` and on every pull request, on `ubuntu-24.04`: `--only-cleanup-before`,
`--only-setup`, `--only-tap-syntax`, and `--only-formulae` on a pull request.
It uploads the bottles of a pull request as a job artifact. The job reads with
`actions: read`, `checks: read`, `contents: read` and `pull-requests: read`.

[`ci.yml`](../../.github/workflows/ci.yml) runs `make ci` on a pull request:
`mise` installs Python 3.12.16 from `mise.toml` and `mise.lock`, then the
gate runs the unit tests in [`.github/scripts/`](../../.github/scripts/).

[`publish.yml`](../../.github/workflows/publish.yml) runs on
`pull_request_target` with the type `labeled`, and its job runs only when the
pull request has the label `pr-pull`:

1. `brew pr-pull --debug --tap="$GITHUB_REPOSITORY" "<number>"` pulls the
   bottles and the cask changes of the pull request.
2. `Homebrew/actions/git-try-push` pushes the result to `main`.
3. The branch is deleted, unless the pull request comes from a fork.

A pull request without that label is merged as it is and does not run this
workflow. A review moves a pull request to `pr-pull`; the label is the merge
switch.

## 4. The Homebrew tarball

[`brew-tarball.yml`](../../.github/workflows/brew-tarball.yml) runs on a
`workflow_dispatch`, on a pull request that changes the workflow itself, and on
the schedule `0 1 * * TUE` (each Tuesday at 01:00 UTC). The `create_release`
job opens a release with the tag `homebrew-<date>` and makes it the latest. The
`push_tarballs` job runs for `arm64` and `amd64` on `ubuntu-24.04` and
`ubuntu-24.04-arm`. It runs a `cgr.dev/chainguard/wolfi-base` container with
`podman`, installs `curl`, `git`, `zstd`, `posix-libc-utils`, `uutils`,
`gnutar` and `grep`, fetches Homebrew's `install.sh`, and runs it
non-interactively into `/home/linuxbrew`. It then writes
`homebrew-<arch>.tar.zst`, computes the sha1, sha256 and sha512 sums, uploads
the files as job artifacts, and uploads them to the release with `gh release
upload --clobber`, using `GITHUB_TOKEN` from `env`. On a pull request it builds
and uploads the job artifacts only, and opens no release.

The tarball exists so that a Snow Linux image installs the same Homebrew base
every time, instead of running the install script during an image build.
